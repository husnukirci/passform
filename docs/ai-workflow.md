# AI workflow log

How this project is built with Claude Code, and where that went wrong.
One line per friction event, appended as it happens and never
reconstructed after the fact. The working agreement is in `CLAUDE.md`.

Format: `- <phase> | <what happened> | <what changed as a result>`.

## Friction log

- P0 | Phase spec named the latest Nest CLI; its template is Nest 12, which `nestjs-zod` does not yet accept as a peer. | Pinned `@nestjs/*` to 11 and wrote the app files by hand instead of moving the template.
- P0 | Phase spec's API dependency list omitted `reflect-metadata` and `rxjs`, both required peers of Nest. | Added them; noted so later specs list peers.
- P0 | `npm install` crashed with `Cannot read properties of null (reading 'edgesOut')`. Isolated to vitest 4.1 plus npm 10.9's peer resolver with a one-package experiment. | Moved to vitest 5.
- P0 | Phase spec assumed `unplugin-swc` was needed for decorator metadata under vitest. A throwaway constructor-injection test passed without it on vitest 5. | Dropped the plugin and the native `@swc/core` binary; recorded the experiment in the vitest config comment.
- P0 | First lint run flagged the empty `AppModule` class under `no-extraneous-class`, a rule that does not know Nest modules exist for their decorator. | Rule set to `allowWithDecorator` for `apps/api`.
- P0 | Spec said "root `.env`", but neither Nest nor Next reads one from the repo root. | Root `dev` script wraps `concurrently` in `dotenv-cli`; each app still falls back to the documented defaults when run alone.
- P0 | The default page fetches `/health` in a Server Component; a first draft would have been prerendered at `next build` and failed whenever the API was down. | Marked the page `force-dynamic` and render an explicit unreachable state instead of throwing.
- P0 | First `git status` after the typecheck showed `.tsout/` and `next-env.d.ts` untracked. Project references need an emit even for a pure typecheck. | Emit declarations to a gitignored `.tsout/`; documented in ADR 14.
- P0 | First CI run failed in the integration job: the "verify services" step called `redis-cli`, which the runner image does not ship. The spec only asked for `pg_isready` and a curl; the Redis check was an unverified addition. | Replaced with a raw `PING` over bash's `/dev/tcp`, tested locally against the compose Redis first.
- P1 | Spec typed `SearchBody.query` as `unknown`; the test that proves no fitment field reaches the scoring clauses needed to reach inside it. | Kept the public type opaque as specified and narrowed once in the test with a comment saying why.
- P1 | First green `validateImportRow` ended in an eleven-way `undefined` check to satisfy strict types without zod. | Refactored to a `Problems` collector that returns a typed fallback so the row is one literal; suite stayed green through the refactor.
- P1 | Spec's `chunkRanges(totalRows, chunkSize?)` had no rule for `chunkSize < 1`, which would loop forever. | Added a failing test and a `DomainError` guard for the size and for negative or fractional row counts.
- P1 | Test fixtures were first written with a make and a brand that turned out to sit close to real company names. | Renamed both to clearly synthetic compounds before commit and rechecked with grep.
- P2 | A probe before writing any script showed Node's type stripping cannot resolve the domain package's `./types.js` specifiers, so the runtime path ADR 14 describes does not work for scripts that import the domain. | Scripts run through `tsx`; the built API's own runtime import of the domain is left to Phase 4, the first phase whose running app needs it.
- P2 | Model names were first drafted as dictionary words, first names and place names; the web check found 25 of 72 collided with real vehicle models or marques, while all 12 invented-compound makes were clean. | Every model is now an invented compound like the makes; the brand check likewise replaced 14 of 46 brand and supplier names.
- P2 | Two verification subagents exhausted the session's web search budget before the last 19 replacement names were checked. | Checked them against Wikipedia's search API from the shell, with a known real model name as the control that had to return hits.
- P2 | Drizzle's insert types carry `| undefined` on optional columns, so `Required<>` did not make the mapper output explicit and the round-trip test would not typecheck. | Added an `Explicit<T>` mapped type in `mappers.ts` that strips both the `?` and the `undefined`.
- P2 | First `large` seed failed with ENOENT: `npm run -w apps/api` runs scripts from the workspace directory, so `--from .data/large` typed at the repo root pointed at the wrong place. | CLI paths resolve against npm's `INIT_CWD`; the default data directory resolves against the repo root from the script's own location.
- P2 | The root `test:integration` script did not load `.env`, unlike `dev`, so the new database-backed test failed with `DATABASE_URL is not set`. | Wrapped it in `dotenv-cli`; verified `db:migrate` still works with no `.env` present, as in CI.
- P2 | Constraint tests asserted on the error message, but Drizzle wraps the pg error as `cause` and its own message is the failed query. | Assert on `cause.constraint` instead, which names the constraint exactly.
- P2 | Sampling the first seeded rows showed fitment windows on open-ended variants running to 2033. | Capped the placement window at the dataset's last month; the small profile shows zero windows past it.
- P2 | The distribution check found a part with three fitments: a duplicate variant draw was skipped instead of redrawn. | Redraw until the target count is met, with a cap; min is now four as specified.
- P2 | Review found the reseed's `TRUNCATE ... CASCADE` never reached `orders`: cascade follows foreign keys into the listed tables, not out of them, so order lines would vanish while their orders stayed. | `orders` and `imports` are named in the statement; an integration test inserts an order and proves a reseed clears it.
- P3 | Spec named the Elasticsearch client without a major; the latest is 9.x, which sends `compatible-with=9` headers the compose Elasticsearch 8.19 rejects. | Pinned `@elastic/elasticsearch` to 8.x to match the server; the two majors move together from here.
- P3 | Spec asked for `helpers.bulk` with 2,000-document chunks; the helper's types show it flushes by bytes and interval only, with no document-count option. | Drive `client.bulk` directly with explicit 2,000-document chunks; one batch in memory, as the review checklist requires.
- P3 | The integration test's cleanup deleted `parts_inttest_v*` and Elasticsearch refused: wildcard deletes are off by default (`action.destructive_requires_name`). | List the throwaway indices by name and delete each; left the server default alone rather than loosening it for tests.
- P3 | Drizzle's `sql` template bound a JS array as a scalar, so the expected-set query failed with "malformed array literal". | Wrote the equipment clause as an `in (...)` list with `sql.join`; the domain's `unlessSet` rule is mirrored in SQL in the same test.
- P4 | The first Nest controller with an injected service failed `consistent-type-imports`: the rule saw a class used only as a parameter type and wanted `import type`, which would have erased the decorator metadata Nest injects from. | Set `experimentalDecorators` and `emitDecoratorMetadata` in the API's parser options, which the rule honours without type-aware linting; verified the same file now passes unchanged.
- P4 | A runtime probe before any endpoint existed showed `node` cannot load `@passform/domain` from the built API: type stripping keeps `./types.js` as written and no such file exists. Phase 2 had hidden this behind `tsx`. | Relative imports inside the packages use `.ts` and `rewriteRelativeImportExtensions` is on; ADR 14 amended. Probe rerun before touching any API code.
- P4 | The catalog service's first draft passed all unit tests with a field and a method both named `categories` and a `never[]` inferred for the tree's children; vitest transpiles without type checking. | `tsc -b` runs after every module now, not only at the end; both were fixed before the commit.
- P4 | The phase spec says the generator "guarantees" a variant without equipment gets an `ask` hit, and the axle test was drafted against `v_000001`. Reading `synth.ts` showed both are statistical (30% of variants, 10% of rows), and `v_000001` has almost no rear-only rows. | The integration test selects the variant, part and code by SQL for the `ask` case and picks the variant with the most rear-axle rows for the axle case, so neither depends on luck.
- P4 | The first `docs/api.md` samples were captured by a shell loop; the resolve example came back empty because zsh does not word-split an unquoted variable, which only surfaced because every sample was inspected before it was pasted. | Re-ran that one with literal values; every example in the document is a response the running API actually returned.
- P5 | A boot smoke of the Nest app under `tsx` failed with "can't resolve dependencies of the ImportsService": esbuild does not emit decorator metadata, so constructor injection by class type is impossible there. | Dropped the script; the integration test under vitest is the boot check, and the built app is the other runtime.
- P5 | The first integration run killed the vitest worker with a 4 GB heap after 28 s and no test output; vitest's buffered console was lost with the process, so progress markers printed nothing until `--disable-console-intercept`. Root cause: BullMQ 6 treats ioredis as an optional peer and loads it with `require`, which a native ES module lacks, so every connection failed and retried forever. | Installed ioredis 5 (the version BullMQ 6 develops against) and registered `RedisConnection.clientFactory` once in the queues module; noted the console flag for the next crash.
- P5 | Spec fixed `jobId = "<importId>:<seq>"` and `"rebuild:<importId>"`; BullMQ 6 refuses custom ids containing a colon ("Custom Id cannot contain :"), which only surfaced as a 500 from `POST /imports` in the integration test. | Hyphen separators; import ids are `imp_<hex>` so the split is unambiguous. ADR 8 and the tests carry the new format.
- P5 | Spec item 5 said an import is `partial` only when a chunk failed; item 9 expected `partial` for a file whose rows were all rejected in one chunk while every chunk was `done`. | Followed item 9: `completed` means every row is in, so a rejected row makes the import `partial` as much as a failed chunk does. Written into ADR 8.
- P5 | Spec item 3 orders "enqueue jobs, then set status running"; a chunk can finish before the next statement runs and the completion listener would then be overwritten by `running`. | The import is `running` before the first job exists, and `finish` only moves an import that is still `queued` or `running`. The service unit test asserts the call order.
- P5 | The health controller unit test booted the whole `AppModule` with invalid service hosts, relying on every client connecting lazily; the queue workers connect at init, so the test failed with "REDIS_URL is not set" and would have hung on close with a fake host. | The test boots the controller alone like the other controller tests; the integration files boot `AppModule` against the compose services and now carry the wiring check.
- P5 | The throughput script's search loop was a background subshell that checked for its sentinel file before the script created it, so it exited without sending a request; noticed only because the tally was empty when the import was 40% through. | Restarted the loop by hand for the rest of the run and said so in `docs/numbers.md` instead of quoting a full-run figure.
- P6 | The repository's `find` sorted lines by SKU while creation kept the request order, so `GET /orders/:id` and the stored response disagreed for a two-line order; the integration test's "GET returns the created body" assertion caught it. | Order lines now carry a `position` column and read back in the order they were sent; migration `0001` adds it.
- P6 | `drizzle-kit generate` emitted `ADD COLUMN "position" integer NOT NULL`, which failed on the dev database because an earlier failed run had left order lines behind; on an empty database it would have passed and hidden the problem. | Hand-edited the migration to add the column nullable, backfill by part id within each order, then set `NOT NULL`; the schema test still applies it from nothing.
- P6 | Spec fixed the repeatable job as `jobId: "reservations.release"`; BullMQ 6 schedules repeats through `upsertJobScheduler(id, { every })` and the old `repeat` option is deprecated, and its scheduler reports `every` as a number where the first assertion expected a string. | One scheduler under the fixed id, asserted by listing the queue's schedulers; the running app proved the job fires (an order expired 29 s after its reservation was backdated).
- P6 | A test compared the second confirm's body with the first after the test itself had moved `expires_at` into the past, so `expiresAt` differed and the assertion failed for a reason unrelated to the behaviour under test. | Assert on `status` and `confirmedAt`, which is what a repeated confirm has to keep.
- P6 | Ten concurrent supertest requests against one server tripped Node's `MaxListenersExceededWarning` in the two race tests. | The test raises the server's listener limit once, with the reason in a comment, rather than splitting the race into smaller batches that would not race.
